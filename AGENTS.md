# Contributor and coding-agent guide

Read this before changing code. It applies to humans and coding agents (Codex, Claude, etc.).

## Commands

- `npm run typecheck`: must pass (TypeScript strict, `noUncheckedIndexedAccess`).
- `npm test`: must pass. Add tests for any change to `src/engine` or `src/data`. Component tests live in `src/test/components` (jsdom; start the file with `// @vitest-environment jsdom`).
- `npm run build && npm run e2e`: run before finishing UI work that touches the core workflow. It ends with an axe accessibility audit; new violations fail the run.

## Layering (enforced by convention)

```
src/domain   types, money (integer cents), dates (ISO, no time zone), ids     ← no imports from other layers
src/engine   pure calculations: csv, dedupe, categorise, cashflow, recurring,  ← imports domain only
             flexibility, scoring, projection, sensitivity, anomalies, insights
src/data     Dexie persistence, import pipeline, decisions, backup, demo data  ← imports domain + engine
src/hooks    React hooks that read data and memoise engine results
src/ui       generic UI primitives, charts, theme
src/features one folder per page/module
```

- Engines are pure functions: no React, no Dexie, no `Date.now()` (pass `today` in). This keeps them testable.
- UI components must not contain financial logic; put it in `src/engine` and test it.

## Financial correctness rules

- Money is **integer cents** (`Cents`). Never parse money with `parseFloat(x) * 100`; use `parseMoney`. Round only at outputs of models.
- Signs: negative = money out, positive = money in, everywhere.
- Dates are `YYYY-MM-DD` strings in local calendar terms; never convert bank dates to `Date` instants for logic.
- Transfers and savings contributions are not spending. Category `kind` decides treatment.
- Never invent data in the user's tables. Demo data is generated by `src/data/demo`, flagged `isDemo`, and removable.
- Decision snapshots are immutable. Do not regenerate or edit `decision.snapshot` after a choice is recorded.
- Every new metric needs a definition (see `src/ui/definitions.ts` and `docs/CALCULATIONS.md`).
- Present estimates and projections as such (provenance badges, “illustrative” wording). Show sample sizes for any insight.

## Persistence changes

- New tables, new or changed indexes, or changes to the meaning/shape of existing data: update `src/domain/types.ts`, add a new `this.version(n)` in `src/data/db.ts` (never edit an old version) with an `.upgrade()` if data must change, bump `BACKUP_VERSION` and add a step to `migrateBackup`, update `docs/DATA_MODEL.md`, and add tests (including an upgrade test).
- New **optional, non-indexed** fields that older records can simply lack: no Dexie version or backup version is needed — update the types, the zod schema if validated, `docs/DATA_MODEL.md`, and add a test.

## Privacy

No network calls with user data, no analytics, no third-party scripts or fonts (the production CSP forbids them). Do not log transaction data to the console. Use only synthetic data in tests, fixtures and screenshots.

## Style

Prettier-style formatting (2 spaces, single quotes, 160-column lines), function components, Tailwind utility classes with the semantic colour tokens defined in `src/index.css` (`bg-surface`, `text-ink-2`, …). Keep dependencies minimal; justify any new one in `docs/ARCHITECTURE.md`.
